# 文档更新器 (Doc Updater)

## 概述

此技能确保项目的工程文档 (`docs/`) 和功能变更日志 (`changelogs/`) 保持准确和最新。它将文档从静态的后期工作转变为开发生命周期中不可或缺的实时组成部分。

## 工作流：实现后的文档维护

在完成代码修改或实现新功能后，必须执行以下强制性工作流：

### 1. 识别受影响的模块
根据更改范围，确定 `docs/` 中需要更新的文档：
- **认证/用户**: `docs/auth_module.md`
- **沙箱/容器**: `docs/sandbox_module.md`
- **SCM/Git/令牌**: `docs/scm_module.md`
- **代码审查/Webhook**: `docs/code_review_module.md`
- **代理逻辑/图**: `docs/agents_module.md`
- **基础设施/Docker**: `docs/docker_infra_module.md`

### 2. 更新模块文档
对于每个受影响的模块：
- 更新 **“功能详情”** 章节，添加新功能。
- 如果内部逻辑、模式 (Schemas) 或依赖项发生变化，更新 **“技术实现”** 章节。
- 如果更改影响效率或可靠性，调整 **“性能/质量指标”**。
- 确保 **“维护建议”** 仍然适用。

### 3. 在变更日志中记录
为当天创建或追加变更记录：
- **路径**: `changelogs/YYYY-MM-DD.md` (例如 `changelogs/2026-03-20.md`)。
- **格式**:
  ```markdown
  ## [变更标题] (YYYY-MM-DD)
  - **摘要**: 变更的简要描述。
  - **原因**: 为什么要进行此更改？
  - **影响**: 受影响的文件/模块。
  - **验证**: 如何验证的？
  ```
- **合并规则**: 如果当天的文件已存在，将新条目追加到文件顶部。

### 4. 同步索引
如果添加了新的文档文件或重大功能区域，更新 `docs/index.md` 以反映新的结构或重点。

## 准则

- **主动执行**: 不要等待用户要求提供文档。文档是“完成定义 (Definition of Done)”的一部分。
- **清晰准确**: 使用代码库中使用的确切文件路径、类名和技术术语。
- **简洁有力**: 变更日志条目应侧重于“是什么”和“为什么”。将详细的“怎么做”留给 `docs/` 中的模块文件。
- **标准格式**: 严格遵守初始文档集中建立的 Markdown 结构。

## 示例场景

**用户**: “在 SCM 模块中增加对 GitLab OAuth 的支持。”
**代理行动**:
1. 在 `app/routers/scm.py` 和 `app/services/scm/` 中实现 GitLab OAuth 逻辑。
2. **更新 `docs/scm_module.md`**，包含 GitLab OAuth 的详细信息。
3. 如果修改了共享认证逻辑，**更新 `docs/auth_module.md`**。
4. **创建/更新 `changelogs/2026-03-20.md`**，记录 GitLab OAuth 条目。
5. 向用户报告完成情况。
