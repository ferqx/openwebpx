## 审查与修复收敛到同一线程队列 (2026-03-26)

- **摘要**: 将代码审查后的修复执行收敛到 `ReviewRun.thread_id` 对应的既有任务线程，审批后的 fix request 不再启动独立 fix 线程，而是按同线程 FIFO 队列串行追加执行。
- **原因**:
  - 任务线程背后绑定容器、仓库拉取和依赖安装，创建新线程的成本高。
  - 审查与修复本质上只是同一工作线程中的不同消息阶段，应复用已有执行环境。
- **后端影响**:
  - app/services/code_review/fix_runner.py 改为直接在既有 `thread_id` 上调用 Aegra `create_run`，把修复指令作为新的 human message 追加到原线程。
  - app/services/code_review/fix_service.py 新增轻量 per-thread queue 处理：`approved` 视为已入队，线程空闲时再转为 `running`，并在前一个 fix run 结束后按 FIFO 拉起下一个。
  - tests/test_code_review_fixes.py 补充线程忙时不立即启动、同线程 FIFO 出队以及完成后续跑下一项的服务层回归测试。
- **前端影响**:
  - web/src/business/portal/portal-code-review-detail.tsx 将 `approved`/`fix_request_approved` 文案收敛为“已入队”。
  - web/src/business/portal/portal-code-review-sidebar.tsx 将 fix request 的 `approved` 状态文案改为“排队中”，时间线文案改为“修复已入队”。
  - web/src/hooks/use-portal-code-review-state.ts 将审批成功提示改为“修复请求已进入关联线程队列”。
